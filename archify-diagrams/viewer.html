🔄 Flujos de Procesos Principales

Certificación, Búsqueda de Candidatos, Asignación (H1-H3)

FLUJO 1: CERTIFICACIÓN (BO-003, H1-H3) Evaluador ├─ Abre pantalla de certificación ├─ Sistema carga: Colaborador + Competencia + Evidencias ├─ Revisa evidencias (formación, práctica, GitLab) ├─ Decisión: ¿Evidencia válida? │ ├─ SÍ → Aprueba nivel │ └─ NO → Rechaza + registra motivo ├─ Sistema registra certificación (auditable) └─ Notifica a colaborador FLUJO 2: BÚSQUEDA DE CANDIDATOS (BO-002, H1-H3) PM (Jefe de Proyecto) ├─ Abre búsqueda de candidatos ├─ Declara requerimiento: Rol-Nivel + Competencias ├─ Sistema calcula brecha para cada colaborador ├─ Muestra candidatos ordenados por menor brecha ├─ Valida candidatos └─ Recomienda al Jefe de Ingeniería FLUJO 3: ASIGNACIÓN (BO-002, H1-H3) Jefe de Ingeniería ├─ Recibe recomendación de PM ├─ Valida candidatos ├─ Asigna uno o varios colaboradores │ └─ Puede asignar incluso bajo nivel (con advertencia) ├─ Sistema registra asignación (auditable) └─ Asignación completada PRINCIPIOS: ✓ Human-in-the-loop: evaluador o Jefe de Ing. decide ✓ Trazabilidad: cada acción registrada + auditable ✓ Transparencia: colaborador ve su perfil y propuestas ✓ Evidencia: todas las decisiones respaldadas por datos

⚡ Web Request with Cache Miss Flow

Secuencia: Browser → API → Redis (check) → PostgreSQL (query) → Redis (fill) → Response

Browser API Server Redis PostgreSQL │ │ │ │ │ HTTP GET /api/data │ │ │ ├────────────────────────────>│ │ │ │ │ │ │ │ │ GET cache_key │ │ │ ├────────────────────────>│ │ │ │ │ │ │ │ nil (cache miss) │ │ │ │<────────────────────────┤ │ │ │ │ │ │ │ SELECT * FROM users │ │ │ ├─────────────────────────────────────────────>│ │ │ │ │ │ │ rows (user data) │ │ │<─────────────────────────────────────────────┤ │ │ │ │ │ │ SET cache_key (TTL 3600s) │ │ ├────────────────────────>│ │ │ │ │ │ │ 200 JSON response │ │ │ │<────────────────────────────┤ │ │ │ │ │ │ FASES: 1. Request: Browser enviía HTTP GET 2. Cache Check: API consulta Redis, resultado = nil (cache miss) 3. Database Query: API consulta PostgreSQL en fallback 4. Cache Replenish: API llena Redis con TTL de 3600s (1 hora) 5. Response: API retorna 200 JSON al Browser RENDIMIENTO: - Cache Hit (próximas requests): ~5ms (Redis only) - Cache Miss (primera request): ~500ms (Database query) - Cache Fill: Asincrónico, no bloquea la respuesta GARANTÍAS: ✓ Source of Truth: PostgreSQL es la autoridad ✓ TTL: Cache expira automáticamente después de 1 hora ✓ Transparencia: API controla cache, cliente no conoce implementación
